**審查者補充發現：**
- OFFICIAL HOST MINIMUM FOR FC/NFS MD EXISTS: VCF 9.1 General FAQs (https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs): 'A new VCF 9 deployment requires a minimum of 4 hosts for the management cluster which is deployed using vSAN, NFS or VMFS on FC' and 'From VCF 9 the management cluster can be configured using vSAN ready nodes (recommended)'. Use this instead of the 'open question' framing; the customer's 6 hosts comply.
- DOCUMENTATION CONFLICT TO DISCLOSE: the VCF 9.1 design 'Storage Models' page (techdocs .../9-1/design/vmware-cloud-foundation-concepts/storage-models.html) still says 'Fibre Channel can be used as supplemental storage for the management domain ... and can also be used as principal storage in a management domain converted from vSphere infrastructure' (asterisk = converge only), and KB 392993 says 'non-vSAN clusters are not supported within the Management Domain'. KB 416270, the VCF 9.1 General FAQs, the 9.1 VCF Installer wizard pages and the Nov-2025 blog all say FC/NFSv3 greenfield MD is supported. Recommend the reply cite the KB/FAQ/Installer pages and have Broadcom support confirm in writing (Support-standard question from the customer).
- SINGLE HARDWARE VENDOR RULE: 9.1 Preparing ESX Hosts page: 'All VMware ESX hosts within the management domain must originate from a single hardware vendor. Cross-vendor hardware configurations in the management domain are not supported.' Relevant to the customer's M2 purchase and to any later plan to add vSAN ReadyNodes to the MD as a second cluster.
- NIC MINIMUM (official, 9.1 Planning and Preparation, techdocs .../9-1/planning-and-preparation.html): 'All physical NICs must have a minimum speed of 10 Gbps for ESX hosts in VCF environments.' For vSAN ESA, 10 GbE is the minimum and 25 GbE or higher is recommended; KB 372311 warns 'System performance may degrade when cluster capacity utilization exceeds 75% and vSAN ESA is configured with 10Gb networking.' So answer 'at least 10GbE' = yes for the FC MD, but 25GbE should be specified now if vSAN ESA is planned later.
- STRETCHED-CLUSTER DEPENDENCY ON THE MD: 9.1 'Stretching Clusters' page: 'The default management domain vSphere cluster must be stretched before a workload domain cluster can be stretched to ensure that the NSX control plane and management VMs remain accessible.' If the MD default cluster is FC (not a vSAN cluster that SDDC Manager can stretch), future vSAN stretched clusters in VI WLDs may be blocked unless the MD is stretched via vMSC (KB 417356); whether a vMSC-stretched FC MD satisfies this prerequisite is not stated in any extract found. Flag as a verification item with Broadcom before purchase.
- LICENSING ALREADY INCLUDES vSAN CAPACITY: VCF licensing gives '1 TiB of vSAN capacity for each Core licensed for VCF' (KB 313548 / VCF SPD), distributable across clusters, with add-on TiB purchasable; and 'For vSphere clusters (aka compute-only clusters or vSAN Compute Nodes) that mount remote datastores, no vSAN license is required on the client cluster.' The customer's VCF-licensed 6 hosts therefore already carry vSAN capacity entitlement for a later vSAN cluster.
- VSAN STORAGE CLUSTERS IN 9.1 AS THE EXPANSION PATH: VCF 9.1 'allows vSAN storage clusters to mount and use both vSAN OSA and vSAN ESA clusters, and vSAN compute-only clusters can also mount vSAN OSA and vSAN storage clusters at the same time'; remote datastore mounting 'can occur within and across different vCenter Servers instances' and 9.1 adds 'sharing storage across workload domains within a VCF install'. Also 9.1 lists a 'vSAN Storage Client' host commissioning storage type. This offers a route to consume vSAN later from non-vSAN compute hosts, but whether a VMFS-FC principal-storage cluster inside VCF can additionally mount a remote vSAN datastore as supplemental storage was not confirmed by any extract (one extract says vSAN 'is configured only as principal storage'; another lists vSAN OSA/ESA among supplemental options). Verify with Broadcom before promising it.
- ALTERNATIVE ARCHITECTURE - CONVERGE M1: Official blogs (How to Converge a vSphere Environment to VCF 9.0; Deployment Pathways) state converge minimums of '3 vSAN ready nodes or 2 vSphere hosts configured using NFS or VMFS on FC', that clusters must already use vLCM images ('VCF 9 does not support vSphere LCM baselines'), and 9.0.1 Installer added convergence of vCenters with existing NSX registrations. The customer's existing M1 (4 hosts, vSphere 8.0 U3, SAN) could be converged into a VCF MD and M2 added as a VI workload domain; M1's vCenter/ESX version must meet the converge support matrix (not captured in extracts).
- CONSOLIDATED vs STANDARD: VCF 9.x supports a consolidated model (management + customer workloads in the MD cluster isolated by resource pools; 9.x Tenancy Deployment Model 1) intended for small-scale environments; Broadcom recommends the standard model. With only 6 hosts, the customer will likely start consolidated and later migrate workloads to a VI WLD ('create a VI workload domain and move the customer workload VMs from the compute resource pool'). This should be in the minimum-architecture answer.
- VCF INSTALLER KNOWN ISSUE (9.0 release notes, vcf-installer-90-known-issues): 'if you specify 1 for the Failures to Tolerate (FTT), the deployment wizard says that three ESX hosts are required, when high availability requires a minimum of four ESX hosts' - do not rely on the wizard's 'Required hosts' figure for sizing.
- VVOLS: deprecated from VCF 9.0 / VVF 9.0 (KB 401070), 'support continuing for critical bug fixes only'; vVol->vSAN is the only supported cross-type MD migration (KB 435850). Advise the customer not to introduce vVols on the SAN.
- VCF 9.1.1 GA: a VCF blog dated 2026-09-03 announces general availability of VMware Cloud Foundation 9.1.1; the reply should reference 9.1.x (latest 9.1.1) rather than 9.1.0 for a new deployment. Details of 9.1.1 storage changes were not captured in extracts.
- HOST-PREP PITFALLS (official KBs found): KB 394521 'SDDC Manager Reports No suitable hosts available ... When Adding Commissioned Hosts Using VMFS on Fibre Channel', KB 431383 (datastore name mismatch error), KB 437715 and KB 432318 - all point to pre-creating an identically named VMFS-6 datastore on every host before commissioning. For NFS-based MDs, Installer pre-validation commonly fails on VMkernel port-group name mismatch, MTU 9000 not end-to-end, and export ACLs.
